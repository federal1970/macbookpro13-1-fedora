# CS8409 on MacBookPro13,1 (subsystem 0x106b3300): the replay driver decoded to register level

Groundwork for adding Apple support to the in-tree `snd-hda-codec-cs8409`. This document turns the
reverse-engineered, replay-style out-of-tree driver (davidjo/snd_hda_macbookpro) into a description
of what is written where, in the vocabulary of the in-tree driver.

Written 2026-10-03 from a read-only pass over the sources. Nothing here was verified on hardware in
this pass, except where the machine's own codec dump is quoted.

## 0. Sources, conventions, confidence labels

**Replay sources** (`/home/user/snd_hda_macbookpro/patch_cirrus/`, checkout at 89b22ff plus one local
uncommitted diff in `cirrus_apple.h`):

| Short name used below | File | Role |
|---|---|---|
| `apple.h` | `cirrus_apple.h` | probe (`cs8409_apple()`), codec ops, PCM prepare wrappers, unsol entry point |
| `new84` | `patch_cirrus_new84.h` | primitives (coefficient access, I2C), per-subsystem dispatch, PCM hooks, unsol queueing |
| `boot84` | `patch_cirrus_boot84.h` | boot helpers: codec walk, vendor node init, GPIO, CS42L83 reset/init, amp reset |
| `real84` | `patch_cirrus_real84.h` | the main replay: boot sequence, speaker path, mic paths, headset path, jack state machine |
| `i2c84` | `patch_cirrus_real84_i2c.h` | CS42L83 I2C sequences, one function per Apple method |

**Line numbers.** `file:line` refers to the working tree as it is now. For `cirrus_apple.h` the local
diff shifts lines relative to upstream HEAD 89b22ff: lines up to 1371 are identical; working lines
1460-1530 are HEAD + 88; working lines from 1544 on are HEAD + 101 (so `cs8409_apple()` is
`apple.h:2708` here and line 2607 upstream). The other four files are unmodified.

**In-tree reference** (Linux 7.2, copies in `/home/user/snd_hda_macbookpro/build/hda/codecs/cirrus/`):
`cs8409.c.orig`, `cs8409-tables.c`, `cs8409.h.orig`.

**Register names** come from kernel v7.2: `include/sound/cs42l42.h` (the register and bit
definitions; `sound/soc/codecs/cs42l42.h` only holds the private struct), `sound/soc/codecs/cs42l83-i2c.c`
(CS42L83 reset defaults), `sound/soc/codecs/cs42l42.c`, `sound/soc/codecs/ssm3515.c`.

**Values** are quoted in hex exactly as written in the source (I2C data is written there as 16-bit
literals such as `0x0083`; only the low byte reaches the bus, see 2.3).

**Confidence labels in the "meaning" columns**

- no label: register name and bit meaning taken from a kernel header or from an in-tree table comment.
- INFERRED: derived by comparing values, not stated anywhere authoritative.
- AUTHOR: the replay author's own annotation (from the Windows `cs4208_38.inf`, the CS42L42 datasheet,
  or disassembly of AppleHDA); quoted, not independently checked.
- UNKNOWN: no basis found. Not guessed.

**Where the replay's numbers come from.** The replay was produced from logged AppleHDA verb traces.
Most "expected value" arguments of `snd_hda_codec_read_check()` / `snd_hda_coef_item()` come from a
MacBookPro14,3 capture, not from a 13,1: the logged subsystem id is `0x106b3900` (`boot84:23`,
`boot84:60`), and the logged pre-init coefficient `0x59` holds `0x0074`, a MAX98706 address
(`boot84:1508`). A mismatch only produces a `codec_dbg` line (`new84:496-524`, `new84:580-593`), so
these values do not drive behaviour, but they are not evidence about the 13,1 either.

Nids that differ between MacBooks and iMacs are stored in the spec: MacBooks use internal mic pin 0x44
-> ADC 0x22 and line-in pin 0x45 -> 0x23; iMacs swap them (`apple.h:3050-3063`). The matching
coefficient bits: `reg9_intmike_dmic_mo` = 0x0020 (MacBook) / 0x0080 (iMac) (`apple.h:3107-3114`),
`reg82_intmike_dmic_scl` = 0x0001 / 0x0002 and `reg82_linein_dmic_scl` = 0x0002 / 0x0001
(`apple.h:3129-3138`). `reg9_linein_dmic_mo` is never assigned, so it is 0.

The spec fields `gpio_mask` (0x0f for 3300, `apple.h:2857-2859`), `gpio_dir`, `gpio_data` are set but
never read by the replay; the GPIO verbs use literals (3.2).

## 2. Primitives

### 2.1 Raw HDA verbs

All through `snd_hda_codec_write()` / `snd_hda_codec_read()` (uncached, so nothing enters the regmap
cache). Wrappers: `snd_hda_codec_read_check()` (`new84:580`) reads and, if the trailing index is > 0,
logs a mismatch against the logged value.

| Nid | Verbs used | Purpose |
|---|---|---|
| 0x00 root | `AC_VERB_PARAMETERS` | vendor id / revision reads (`boot84:15-19`, `real84:3169`) |
| 0x01 AFG | `AC_VERB_SET/GET_POWER_STATE` via `hda_set_node_power_state()` (`new84:118`, waits up to 500 ms in `hda_sync_power_state_8409()` `new84:50`) | D0 before every I2C access and at play/capture; D3 at playback stop |
| 0x01 AFG | `AC_VERB_SET_GPIO_MASK`, `_DIRECTION`, `_DATA`, `_WAKE_MASK`, `_UNSOLICITED_RSP_MASK`, `AC_VERB_GET_GPIO_DATA` | GPIO, see 3.2 |
| 0x01 AFG | verb `0xfff`, payload 0 (`new84:599`) | logged raw as `0x001fff00` and labelled "AC_VERB_DBL_CODEC_RESET" (`boot84:34`). Not `AC_VERB_SET_CODEC_RESET` (0x7ff). Effect UNKNOWN (AUTHOR: "still not clear if this does anything", `new84:598`) |
| 0x01 AFG | verb `0x7f0`, payload `0xb7` (`boot84:1850`) | last verb of `AppleHDAFunctionGroupCS8409::enableGPIforUR`. UNKNOWN verb. See 7.2 |
| 0x47 vendor widget | `AC_VERB_SET_PROC_STATE` 1 | "enable VPW processing", issued before every I2C access (`new84:263`, `new84:362`) and at many other points |
| 0x47 | `AC_VERB_GET_COEF_INDEX`, `AC_VERB_SET_COEF_INDEX`, `AC_VERB_GET_PROC_COEF`, `AC_VERB_SET_PROC_COEF` | coefficient access, 2.2 |
| 0x47 | verb `0x7f0`, payload `0xb6` or `0x00` | last verb of `AppleHDATDMBusManagerCS8409::configureTDMUR`. UNKNOWN verb. See 7.2 |
| 0x02, 0x03, 0x0a (ASP1 out A, ASP1 out B, ASP2 out A) | `AC_VERB_SET_STREAM_FORMAT`, `AC_VERB_SET_CHANNEL_STREAMID`; also `snd_hda_codec_setup_stream()` | output converters |
| 0x1a (ASP2 in A), 0x22 (DMIC1), 0x23 (DMIC2) | same, plus `AC_VERB_SET_POWER_STATE`, `AC_VERB_SET_CONNECT_SEL` 0, `AC_VERB_SET/GET_AMP_GAIN_MUTE`, `AC_VERB_GET_CONV` | input converters |
| 0x24, 0x25, 0x2c, 0x3c, 0x44, 0x45 | `AC_VERB_SET/GET_PIN_WIDGET_CONTROL` | 0x40 (OUT_EN) speakers, 0xc0 (HP_EN and OUT_EN) headphone, 0x20 (IN_EN) inputs, 0x00 off |
| 0x44, 0x45 | `AC_VERB_SET_AMP_GAIN_MUTE` | pin input amp ("boost") := 0 |
| all pins 0x24-0x45 | `AC_VERB_SET_PIN_WIDGET_CONTROL` 0 at boot (`boot84:672`...`1348`) | clear pin controls |
| 0x46 beep | `AC_VERB_SET_BEEP_CONTROL` 0 (`boot84:1362`) | beep off |

The mapping of converters to pins follows the in-tree enum (`cs8409.h.orig` `CS8409_PIN_*`):
0x02 `ASP1_OUT_A` -> 0x24 `ASP1_TRANSMITTER_A`; 0x03 `ASP1_OUT_B` -> 0x25 `ASP1_TRANSMITTER_B`;
0x0a `ASP2_OUT_A` -> 0x2c `ASP2_TRANSMITTER_A`; 0x3c `ASP2_RECEIVER_A` -> 0x1a `ASP2_IN_A`;
0x44 `DMIC1_IN` -> 0x22 `DMIC1`; 0x45 `DMIC2_IN` -> 0x23 `DMIC2` (also `apple.h:84-94`).

Stream bookkeeping uses a private redefinition of the HDA core's `struct hda_cvt_setup`
(`new84:645-652`) to reach into `codec->cvt_setups` and force `snd_hda_codec_setup_stream()` to
re-send (`new84:790`, `810`, `839`). This has no register-level content but is a layering hazard (7.9).

Sequence of one replay I2C write (`new84:349-441`):

1. AFG -> D0 (`new84:359`); `AC_VERB_SET_PROC_STATE` 1 on 0x47 (`new84:362`).
2. coef 0x00 |= 0x8 (I2C clock on) (`new84:365`).
3. coef 0x59 (`CS8409_I2C_ADDR`) := `i2c_address`, the 8-bit write address (7-bit address << 1; the
   in-tree driver uses the same convention, `CS42L42_I2C_ADDR (0x48 << 1)`).
4. if `paged`: coef 0x5d (`CS8409_I2C_QWRITE`) := `i2c_reg >> 8`, i.e. device register 0x00 := page;
   then poll coef 0x5c (`CS8409_I2C_STS`) until `(sts & 0x18) == 0x18`, up to 8 retries with
   `usleep_range(2000,4000)` (`new84:374-395`).
5. coef 0x5d := `((i2c_reg << 8) & 0xff00) | (i2c_data & 0xff)` (register low byte, data byte)
   (`new84:403-405`).
6. poll coef 0x5c as in 4 (`new84:409-430`). No error path: the function carries on whatever the status.
7. coef 0x00 &= ~0x8 (I2C clock off) (`new84:432`).

A read is the same with step 5 replaced by coef 0x5e (`CS8409_I2C_QREAD`) := `(i2c_reg << 8) & 0xffff`
and a final read of coef 0x5e (`new84:303-334`).

Differences from the in-tree helpers, for whoever ports this:

- the in-tree driver caches the device address (`cs8409_set_i2c_dev_addr()` `cs8409.c.orig:163`) and
  the page (`cs8409_i2c_set_page()` `cs8409.c.orig:180`, `scodec->last_page`); the replay rewrites
  both on every access;
- completion test: in-tree `retval & 0x18` (either bit) with a 20 ms timeout
  (`cs8409_i2c_wait_complete()` `cs8409.c.orig:150`); replay `(retval & 0x18) == 0x18` (both bits),
  8 tries. Which bit means "done" and which "ack/error" is UNKNOWN from these sources;
- the in-tree driver serialises with `spec->i2c_mux`; the replay has no locking and instead queues
  unsolicited responses behind `spec->block_unsol` (`new84:1319-1338`, NOTES.md);
- `paged` in the replay is a per-call argument; in-tree it is `sub_codec.paged`.

I2C bus setup (once, `enable_i2c()` `boot84:1657`, `AppleHDAFunctionGroupCS8409::enableI2C`):
coef 0x00 := 0x9008, coef 0x02 := 0x0080, coef 0x5b := 0x0010, coef 0x00 := 0x9000. The in-tree
equivalent is `cs8409_cs42l42_init_verbs[]` (`cs8409-tables.c:61-69`): coef 0x02 := 0x0080 ("I2C
mode"), coef 0x5b := 0x0200 ("100kHz I2C_STO = 2"). Apple's 0x5b value 0x0010 is not explained by any
source here: UNKNOWN (the logged pre-init read of 0x5b is already 0x0010, `boot84:1510`).

### 5.4 Interrupt delivery and decoding

- Unsolicited responses reach `cs_8409_cs42l83_jack_unsol_event()` (`apple.h:1756`). The tag is
  extracted and logged (`apple.h:1761`, `1778`) but not used for dispatch. AUTHOR: the tag observed is
  0x37 (`apple.h:3148`), and no `AC_VERB_SET_UNSOLICITED_ENABLE` is ever sent because "unsolicited
  response is pre-enabled" (`apple.h:943-946`). The only enables the replay writes are the GPIO
  unsolicited mask 0x01, coef 0x71 and the two 0x7f0 verbs.
- Responses arriving while a verb block is running are queued (up to 10) and replayed afterwards
  (`new84:1319-1338`, `1285-1302`).
- `cs_8409_external_device_unsolicited_response()` (`real84:3437`): GPIO data bit 0 high -> nothing to
  do (`real84:3449-3454`). Otherwise, up to 11 rounds of: read 0x1b7b, 0x1b7c, 0x1308 `CODEC_STATUS`,
  then 0x1301-0x1305, 0x130b, 0x130d, 0x130e, 0x130f (`real84:3696-3718`), re-read GPIO, `msleep(10)`,
  until GPIO0 is high again (`real84:3589-3618`). Then the masks 0x1b79 `DET_INT1_MASK`, 0x1b7a
  `DET_INT2_MASK`, 0x131b `CODEC_INT_MASK` (`real84:3758-3762`).
- status word = `(0x1b7b << 16) | (0x1b7c << 8) | 0x1308`; mask word likewise; `int_response = ~mask &
  status` (`real84:3726`, `3769`, `3483`).

| `int_response` bit (`real84:4609-4624`) | Register bit | Name | Action |
|---|---|---|---|
| 0x400000 | 0x1b7b bit 6 | tip sense plug (mask bit: `DET_INT1_MASK.TIP_SENSE_PLUG`) | plug-in sequence |
| 0x200000 | 0x1b7b bit 5 | tip sense unplug | unplug sequence |
| 0x100000 | 0x1b7b bit 4 | "button release" (AUTHOR); bit not named in the header | none (`cs_8409_headset_button_event()` is empty, `real84:5299`) |
| 0x020000, 0x010000 | 0x1b7b bits 1, 0 | "button up / down press" (AUTHOR) | none |
| 0x1800 | 0x1b7c bits 4, 3 | "button detect" (AUTHOR; only 0x08 seen); bits not named in the header | button/mic detection |
| 0x0200, 0x0100 | 0x1b7c bits 1, 0 | mask-register names `M_SHORT_RLS`, `M_SHORT_DET` | none |
| 0x02 | 0x1308 bit 1 | `HSDET_AUTO_DONE` | headset type detection |
| 0x01 | 0x1308 bit 0 | `PDN_DONE` | none |

0x1b7b and 0x1b7c are not defined in `include/sound/cs42l42.h`. The mainline ASoC driver, which also
serves the CS42L83, takes the same information from 0x1309 `DET_INT_STATUS1` / 0x130a `DET_INT_STATUS2`
and 0x130f `TSRS_PLUG_STATUS` (`cs42l42.c:1648-1658`); the logged AppleHDA sequences reproduced in the
replay never read 0x1309 or 0x130a.

## 7. Open questions and risks

### 7.1 The SSM3515 accesses are made with `paged=1`

Every SSM3515 call in the replay passes `paged=1` (`boot84:2223-2226`, `real84:1371-1379`,
`real84:1940`), while Apple's log shows plain `i2cWrite` for the amps and `i2cPagedWrite` only for the
CS42L83. With `paged=1`, `cs_8409_vendor_i2cWrite()` / `i2cRead()` first write coef 0x5d :=
`i2c_reg >> 8` = 0x0000 (`new84:374`, `new84:275`), which is a write of 0x00 to device register 0x00,
`SSM3515_PWR`. So in the replay, as it runs on this machine today:

- every amp register access is preceded by `PWR` := 0x00 (amp powered up, auto power-down off);
- the boot "reset" is `PWR` := 0x00 followed by `PWR` := 0x83;
- the amp is powered up before `SAI1`/`SAI2` are programmed, whereas Apple powers it up last;
- power-down is `PWR` := 0x00 then `PWR` := 0x01.

The replay works like this, so it is harmless in practice, but it means the working sequence is not
the logged Apple sequence. An in-tree port with a non-paged device will be the first time the logged
order is actually used on Linux. Low risk, but test for pops and for a first-period dropout.

### 7.2 Verb 0x7f0 and how unsolicited responses are enabled

`0x7f0` with payload 0xb7 on the AFG (`boot84:1850`) and 0xb6 / 0x00 on the vendor widget
(`real84:940`, `1112`, `1769`, `1876`, `3970`, `4045`, `4060`, `4144`, `4185`, `4355`). No raw hex is
preserved for these. Observations, none of them conclusive:

- 0xb7 = 0x80 | 0x37 and 0xb6 = 0x80 | 0x36: the layout of an unsolicited-enable payload (enable bit
  plus 6-bit tag); the tag the driver sees on jack events is 0x37 (`apple.h:3148`);
- the standard verb is 0x708, not 0x7f0, and the author states that AppleHDA never sends
  `AC_VERB_SET_UNSOLICITED_ENABLE` (`apple.h:944`);
- the machine's dump shows the vendor widget with `Unsolicited: tag=00, enabled=0` while idle, which
  is what one would read back after the 0x00 write if 0x7f0 aliased the standard register, but equally
  if it did not.

The in-tree `cs8409_enable_ur()` uses the standard verb on the AFG plus the GPIO unsolicited mask and
works on Dell. First thing to test on hardware: skip 0x7f0, call `cs8409_enable_ur()`, and see whether
a plug event arrives. If the tag matters, `snd_hda_jack_*` assigns its own.

Related: coef 0x71 (`CS8409_ASP_UNS_RESP_MASK`) values 0x400f / 0x800f and the writes of 0x001f to
0x6b / 0x6c. Dell never writes them. They look like ASP-level error reporting ("configureTDMUR") rather
than something audio depends on; untested.

### 7.3 State that may come from Apple firmware

- The pre-init coefficient dump in the log (from a 14,3) already has I2C enabled (0x00 = 0x9008, 0x02
  = 0x0080, 0x5b = 0x0010), a device address in 0x59 and 0x82 = 0xff00 (`boot84:1419-1549`): the EFI
  firmware has used the codec (boot chime). The replay rewrites all of these itself, and the user's
  resume work shows that a full re-run of the boot setup from the codec's power-on state restores
  sound (test report on davidjo/snd_hda_macbookpro#220), so the replay does not depend on firmware state for speakers.
  Not shown for the headset paths.
- Default pin configs are firmware- or strap-provided and are used as they are (3.1).
- "Unsolicited response is pre-enabled" (`apple.h:944-945`) is an assumption of the author; see 7.2.
- coef 0x09 reset value 0x0013 (bits 0x0010 and 0x0003) is taken as given and only ORed into.
- coef 0x58 (`ASP2_H_RX_CTRL2`) is the one slot register not initialised to 0x8000 (3.2 step 20).

### 7.4 Clocking is only known for 44.1 kHz

All ASP clock values (coef 0x01 bit 0x0200, 0x04, 0x05, 0x07, 0x08, 0x11-0x15) and the CS42L83 PLL
setup (0x1502-0x1505, 0x150a, 0x120c) are for 44.1 kHz with a 256-bit frame. The in-tree driver is
48 kHz only. There is no documentation of the CS8409 clock registers in these sources beyond the
in-tree comments, and the two disagree in ways that cannot be resolved by reading (0x04: 0x28ff vs
0x08ff; 0x05: 0x0062 vs 0x0001). Either the Apple path stays at 44.1 kHz with Apple's values, or
someone with the CS8409 documentation (Cirrus) supplies the 48 kHz equivalents. Mixing Dell's ASP
values with Apple's amps is a guess that should not be made without the datasheet.

Also unknown: whether the SSM3515s get a usable bit clock at Apple's settings only because of the
exact `SCDIV` / source-select combination (the amps take BCLK as their only clock).

### 7.5 Jack detection: Apple's flow and Dell's flow use different interrupt sources

Apple: tip sense through 0x1b73/0x1b77 with interrupts on 0x1b79 and status on 0x1b7b; `TSRS` plug
interrupts masked for good. Dell: `TSRS_PLUG_STATUS` / `TSRS_PLUG_INT_MASK` (0x130f / 0x1320) and
`TSENSE_CTL` 0x80. Both end in the same automatic type detection (0x1120 `HSDET_CTL2`, 0x1124). Whether
the tip-sense pin on this board feeds the `TSRS` logic as it does on Dell is UNKNOWN; if it does, the
in-tree `cs42l42_*` functions could be used with a different init table; if not, an Apple variant of
`cs42l42_enable_jack_detect()` / `cs42l42_jack_unsol_event()` on the 0x1b79/0x1b7b pair is needed.
Mainline ASoC `cs42l42.c`, which `cs42l83-i2c.c` reuses unchanged for the CS42L83, takes tip sense
from 0x130f (`cs42l42.c:1658`, `1930`), which suggests the `TSRS` route is at least valid for the
chip; that says nothing about how this board is wired.

The 1800 ms sleep between the tip-sense event and the start of type detection (`real84:4912`), and the
`msleep(0x28)` / `msleep(0x14)` in the bias-off block (`i2c84:536`, `542`), are the timing-critical
parts of Apple's flow. Dell uses 20-25 ms after `HSDET_CTL2` (`cs8409.c.orig:662`) and 100 ms steps in
manual detection.

Button handling relies on bits the CS42L42 header does not name (5.4, 6.3) and is not implemented in
the replay beyond detection (`real84:5299`).

### 7.6 Reset and power-up timing

- No delay in or after the CS42L83 reset pulse (3.3). The in-tree driver waits 10-15 ms after
  releasing reset (`cs8409.c.orig:883`), and `CS42L42_BOOT_TIME_US` is 3000. The replay gets away with
  it because each HDA verb and each I2C access is slow; a port must add the delay.
- The reset pulse is issued twice (`real84:2143`, `2163`), with only status reads in between. No
  visible reason; AppleHDA's `resetDevice` appears to be called from two places (`boot84:1859-1884`).
- No wait for SSM3515 after its software reset (3.4) before the next access.
- I2C completion is polled but never checked (2.3).

### 7.7 Things the replay does twice, or does and undoes, without a visible reason

- the full speaker bring-up and tear-down at boot (3.6);
- `SSM3515_DAC` read and written twice with its reset value (4.2 step 5);
- amps powered down twice at stop (4.3 step 22); headphone mute / power-down block twice at stop
  (5.2); mic mute / power-down twice (5.3);
- 0x1b7a := 0x00ff twice (5.5 step 1, 5.6);
- `MIC_DET_CTL1` := 0x9f twice at boot (3.3 step 58, 3.5 step 62);
- coef 0x00 := 0xb000 then back to its previous value around the ASP1 clock write (4.1 steps 11-13):
  PLL2 is switched on only for the duration of the `ASP1_CLK_CTRL2` write. Could be a required unlock
  or just how AppleHDA's helper works: UNKNOWN;
- coef 0x05 written masked and then in full with the same value (4.1 steps 7, 15); likewise 0x04, 0x07,
  0x08;
- stream ids on 0x02 / 0x03 detached, re-attached and detached again around coef 0x17 at stop (4.3
  steps 2-8, 13, 20);
- `AC_VERB_SET_PROC_STATE` 1 before every I2C access and at many other points;
- three or four consecutive GPIO data reads (`real84:2519-2525`, `3077-3081`).

The detach / write 0x17 / re-attach order in `syncConverters` (4.1 steps 36-41) is the one sequence
here that looks deliberately ordered: both converters are held without a stream while they are added
to the sync group. Keep that order.

### 7.8 Differences between this path and the other Apple machines

- 0x106b3900 (MAX98706) needs GPIO5 (dir/data 0x22, mask 0x27) before talking to the amps
  (`boot84:2180-2205`); the 13,1 has no such GPIO step: its amps appear to be powered without codec
  involvement. Whether GPIO3 (enabled, input, reads 0) has a function on the 13,1 is UNKNOWN.
- iMacs: inverted tip sense, swapped DMIC1/DMIC2, TAS5764x amps with a 10-register init and a separate
  enable step, GPIO4 (dir/data 0x12, mask 0x1f).
- All "expected" values in the replay are from the 14,3. For the 13,1 the only machine-specific logged
  data in these files are the SSM3515 I2C lines (`boot84:2218-2221`, `real84:1361-1369`, `1938`).
- The comment "macbook pro 14,1?13,1" (`apple.h:2766`) shows the author was not certain which models
  share 0x106b3300.

### 7.9 Structural hazards for a port (not register-level)

- AFG put in D3 at every playback stop (4.3 step 23), with further verbs sent afterwards, and D0
  forced before every I2C access. The in-tree driver leaves power to the HDA core; the replay's
  `power_save_node = 0` (`apple.h:2697`) and hand-made power handling must not be carried over.
- The replay reaches into `codec->cvt_setups` with a copied struct definition (`new84:645-673`).
- No locking around I2C; unsolicited handling runs multi-second sequences with `msleep()` and a
  hand-made queue (`new84:1304-1359`). The in-tree mutex and jack helpers replace all of that.
- `cs_8409_capturestop_real()` writes a literal stream id 1 to 0x22 (`real84:3331`).
- `cs_8409_disable_TDM_proper_amps34()` clears coef 0x71 and sends 0x7f0 := 0 unconditionally (4.3
  step 19); `cs_8409_sync_converters_off()` overwrites coef 0x01 with the literal 0x0220 (4.3 step 7).
  Both are wrong if ASP2 is active at the same time; a table-driven port avoids the issue by not
  tearing the configuration down per stream.
- Speaker slot order was changed from Apple's (4.2); decide the channel map from a hardware test
  (which address is which driver), not from either order.

### 7.10 Suggested order of experiments (each needs the hardware)

1. Read back, on the running replay: coefs 0x00-0x18, 0x19-0x1c, 0x29-0x2a, 0x49-0x4a, 0x5b, 0x71,
   0x82 while playing; SSM3515 registers 0x00-0x05 (non-paged read) on all four addresses. This turns
   the INFERRED steady-state column of 6.4 into measured values.
2. Standard unsolicited enable instead of verb 0x7f0 (7.2).
3. Static coefficient table (slots enabled permanently, coef 0x17 = 0x0003, 0x01 = 0x0220) instead of
   per-stream setup; only amp `PWR` toggled in the playback hook.
4. Dell's jack flow on the CS42L83 with Apple's init values (7.5).
5. Which amp address is which speaker (7.9).
